## 1. 部署与更新（云服务器 Docker）

仓库的 [docker-compose.yml](../../docker-compose.yml) 中 **backend 从本地源码构建**，
frontend 拉 GHCR 预构建镜像。改完后端代码的标准发布流程：

```bash
# 本机：提交并推送
git add <改动文件> && git commit -m "fix(scope): 中文描述" && git push origin main

# 服务器：拉代码、重建 backend、滚动重启（postgres/redis/frontend 不动，数据在 volume 不丢）
ssh <用户>@<服务器>
cd ~/quantdinger        # 实际目录用 docker compose ls 查
git pull origin main
docker tag $(docker compose images backend -q) quantdinger-backend:rollback-$(date +%m%d)  # 备份镜像，秒级回滚用
docker compose build backend
docker compose up -d backend

# 验证
docker compose ps                       # backend 应为 healthy（约 30 秒）
curl -s http://localhost:5000/api/health
docker compose logs -f --tail 50 backend
```

回滚：`docker tag quantdinger-backend:rollback-<日期> quantdinger-std-backend:latest && docker compose up -d backend`。

中断窗口约 10–30 秒；运行中的策略随容器恢复，已收盘信号在下一轮处理。

## 2. 环境变量：加在哪里才生效

三个位置作用不同，**优先级从高到低**：

| 位置 | 是否注入容器 | 适用场景 |
|------|------|------|
| `docker-compose.yml` → `services.backend.environment` | ✅ 优先级最高 | 长期固定的部署级配置 |
| `backend_api_python/.env` | ✅（挂载到容器 `/app/.env`，run.py 启动时 `load_dotenv(override=False)` 读取） | **推荐**：不被 git 跟踪，Sync fork 不冲突；改完 `docker compose restart backend` 即生效，无需 rebuild |
| 仓库根目录 `.env` | ❌ **不注入容器** | 只给 compose 做 `${...}` 占位符替换（IMAGE_PREFIX、端口等），别把应用配置写这里 |

注意 `override=False`：同一变量 compose 里设过，`.env` 的值不生效——只在一处设置，避免困惑。

### 2.1 本 fork 关注的关键变量

| 变量 | 默认 | 说明 |
|------|------|------|
| `LIVE_STRATEGY_LOCK_ENFORCE` | `true` | **实盘冲突锁**。上游 v3.0.30 起，同一「API 凭证 + 交易所 + 市场类型 + 交易对」同时只允许一个 running 实盘策略（防多策略互相平仓产生幽灵持仓）。多策略共用 demo/测试网账户做并行实验时可设 `false` 关闭，风险自担；非法取值按 `true` 处理 |
| `AGENT_LIVE_TRADING_ENABLED` | `false` | Agent Gateway 实盘下单总开关；false 时 T 类调用一律记 paper 单 |
| `POSITION_SYNC_INTERVAL_SEC` | `30` | 持仓对账轮询间隔；多策略共用一个 Key 时别调太小，防交易所限频封 IP |
| `CCXT_DEFAULT_EXCHANGE` | `binance` | K 线数据源交易所。币安公共 API 被地理封锁（HTTP 451）时可切 `gate` / `bitget` / `htx`（注意 Gate 只供最近约 1 万根 K 线） |
| `PROXY_URL` / `HTTPS_PROXY` | 空 | ccxt 拉行情走的代理 |

完整清单见 [backend_api_python/env.example](../../backend_api_python/env.example)（每个变量带注释）。

## 3. 实盘 / 模拟盘运行须知

### 3.1 几个容易混淆的概念

- **spot（现货）vs swap（永续合约）**：现货买到真币、不能做空不能加杠杆；
  swap 是无到期日的合约，可做空、可加杠杆、有爆仓风险。双向策略必须用 swap。
- **「模拟盘」**：连接交易所 demo/测试网 API Key 的实盘链路（`execution_mode='live'`），
  订单真实发往交易所测试环境——所以最小下单量、持仓对账这些交易所规则**全部生效**。
- **同账户同合约只有一份持仓**：两个策略用同一账户的 Key 跑同一个 swap 交易对，
  操作的是同一份仓位，互相平仓属于物理现实而非 bug——这就是冲突锁存在的原因。
  要干净并行，用**不同的币安子账户**（同账户的第二把 Key 没用，仓位仍共享）。

### 3.2 启动策略报 409 冲突

`Live strategy conflict: ... Please stop strategy N first.`——按优先级选一个：

1. 停掉占用的策略再启动（提示里给了 ID）；
2. 给新策略换**子账户** API Key；
3. 错开交易对或市场类型；
4. demo 实验场景：`backend_api_python/.env` 加 `LIVE_STRATEGY_LOCK_ENFORCE=false` 后
   `docker compose restart backend`（接受持仓互相干扰）。

## 4. 常见报错速查（实战沉淀）

| 报错特征 | 根因 | 处置 |
|----------|------|------|
| 币安 `Order notional is below MIN_NOTIONAL`，平仓单反复被拒 | 残仓名义价值低于交易所门槛；平台曾把 reduce-only 平仓单也做本地预检（已修复：平仓单豁免，币安 -4164 本就豁免 reduce-only） | 升级到含修复的版本；开仓侧把 `投入金额 × entryPct × 杠杆` 提到 ≥ 20 USDT |
| OKX `51169 don't have any positions in this direction`，每根 K 线重复 close_* | 本地幽灵持仓（交易所端已手动平仓/早前订单实际成交但被记失败），本地持仓表未对账 | 已修复：平仓被"无仓可平"类错误拒绝时自动触发持仓对账清掉幽灵行；日志看 `Position reconciled after close rejection` |
| `Flip open_long skipped: close_short did not clear short` | 上述两类平仓失败的连带症状——反手被阻塞 | 修复平仓问题后自动恢复 |
| 回测收益好得离谱（胜率 >85%、夏普 >2.5） | 大概率是未来函数、连续触发信号、或**过窄的 trailing 在 bar 内模拟的乐观成交**（如 0.03% 追踪幅度 < 滑点） | 全文搜 `shift(-1)`；查边缘触发写法；trailing 设 ≥ 2×滑点再重跑；换标的做外样本验证 |
| pandas 3.x 下信号变成每根 bar 触发且不报错 | `~s.shift(1).fillna(False)` 旧写法在 pandas 3 静默失效 | 边缘触发必须 `shift` 后显式 `.astype(bool)`，模板见新人教程第 3 节坑一 |
| 后端日志 `OKX HTTP 500 "Systems are busy"` 后持仓开始错乱 | 订单提交后响应失败，实际可能已成交（"结果不明"故障） | 自动对账能兜住后果；怀疑时在平台手动停启策略触发同步 |
